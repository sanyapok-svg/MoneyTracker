# Роли пользователей и админ-панель — описание фичи

## О чём фича

После внедрения аутентификации все зарегистрированные пользователи **равны**:
каждый видит только свои транзакции. Нужно ввести **роль администратора** —
владельца приложения, который:

- видит **список всех** зарегистрированных пользователей;
- может **заблокировать** пользователя (запретить вход и работу с приложением);
- может **удалить** пользователя из системы (вместе с его данными по правилам
  каскада, см. ниже).

Обычные пользователи **не** видят админ-раздел и **не** могут вызывать
админские операции.

## Модель ролей (MVP)

Две логические роли:

| Роль        | Кто это                         | Права                                      |
|------------|----------------------------------|--------------------------------------------|
| `user`     | Любой зарегистрированный аккаунт | Только свои транзакции (как в PRD-2)      |
| `admin`    | Владелец приложения             | Плюс: список пользователей, блок, удаление |

**Назначение администратора (MVP):** один супер-админ, email которого задаётся
в конфигурации окружения **на сервере**, без отдельного UI «назначить админа».

- Переменная окружения, например: `ADMIN_EMAIL` (или `APP_ADMIN_EMAIL`).
- Значение — **один** email в нижнем регистре или сравнение **без учёта регистра**
  после `trim()` с email из сессии `auth.getUser()`.
- Владелец копирует в `.env.local` **свой** email тот же, что при регистрации
  / входе в Supabase Auth — тогда при входе этот пользователь считается `admin`.

> Несколько админов, смена админа через UI и роли в БД — **вне scope** этой
> версии PRD (можно отдельной фичей позже).

## Технический стек (май 2026)

- **Next.js 16** (App Router) + TypeScript — как в PRD-2
- **Supabase Auth** — источник правды по пользователям (`auth.users`)
- **`@supabase/ssr`** — сессия пользователя на сервере
- **Supabase Service Role** — **только на сервере** (Server Actions, Route
  Handlers), для вызовов Admin API: список пользователей, бан, удаление
- **RLS** — для обычных пользователей без изменений; админские операции не
  обходят RLS из браузера — они идут через доверенный серверный код с
  service role **после** проверки «текущий пользователь — админ по email»

**Важно:** Service Role Key **никогда** не попадает в клиентский бандл и не
передаётся в браузер.

## Главные функции

### 1. Определение «текущий пользователь — админ»

- Утилита на сервере, например `isAdminUser(sessionUser): boolean`:
  сравнение `sessionUser.email` с `process.env.ADMIN_EMAIL` (нормализация:
  `trim`, желательно `toLowerCase` с обеих сторон).
- Если переменная не задана — **никто** не считается админом (безопасный дефолт),
  либо явно задокументировать поведение «админ-роуты 404» / редирект на `/`.

### 2. Раздел админ-панели в UI

- Отдельный маршрут, например `/admin` или `/admin/users` (на усмотрение
  реализации, в PRD достаточно «единая админ-страница со списком»).
- Доступ:
  - не залогинен → как для защищённых страниц (редирект на `/login`);
  - залогинен, но не админ → **403** или редирект на `/` с коротким сообщением
    «нет доступа»;
  - залогинен и админ → показать панель.

- В шапке основного приложения — ссылка «Админка» **только** если сервер
  определил админа (через серверный компонент / флаг из сессии), чтобы не
  светить URL лишним.

### 3. Список всех пользователей

- Таблица: email, дата регистрации (если доступна из API), статус
  «активен / заблокирован», идентификатор `user_id` (uuid, можно сокращённо).
- Данные получать через **Supabase Auth Admin API** с сервера
  (`listUsers` с пагинацией, если пользователей много — заложить «следующая
  страница» или лимит MVP с пометкой «до N записей»).
- Альтернатива (если команда предпочтёт): таблица `public.profiles`, заполняемая
  триггером при `INSERT` в `auth.users`, и чтение списка из Postgres с
  service role — в PRD допустимы оба подхода; для MVP достаточно Admin API.

### 4. Блокировка пользователя

- Админ нажимает «Заблокировать» у выбранного пользователя.
- Серверная операция: Supabase Admin API — установка бана на аккаунт
  (например, `ban_duration: '876000h'` для «навсегда» до ручного снятия **или**
  явная дата окончания — зафиксировать в реализации один понятный вариант).
- Кнопка «Разблокировать» снимает бан (`ban_duration: 'none'` или эквивалент
  в используемой версии SDK).
- **Нельзя** заблокировать самого себя (проверка `targetUserId !== currentUserId`).
- После успеха — обновление списка (`revalidatePath` для админ-страницы).

### 5. Удаление пользователя

- Админ нажимает «Удалить» → подтверждение (диалог) с предупреждением, что
  данные пользователя будут удалены.
- Сервер: `auth.admin.deleteUser(id)` (или эквивалент в SDK).
- **Каскад:** в миграции PRD-2 уже есть `user_id references auth.users (id)
  on delete cascade` — при удалении пользователя транзакции этого `user_id`
  удаляются автоматически. Если появятся другие таблицы с FK на `auth.users`,
  их тоже нужно перевести на `on delete cascade` или осознанно `set null`.
- **Нельзя** удалить самого себя.
- Опционально MVP: нельзя удалить последнего известного админа по email —
  избыточно, если админ один и тот же env; минимум — запрет удаления `id`
  текущей сессии.

### 6. Аудит и безопасность

- Все действия блокировки и удаления — только после проверки `isAdminUser`.
- Логирование на сервере (опционально MVP): `console` с user id цели и
  временем; полноценный audit log — вне scope.
- Rate limiting для админ-эндпоинтов — nice-to-have, не обязателен в первой
  итерации PRD.

## Переменные окружения

| Переменная        | Где        | Назначение                          |
|-------------------|------------|-------------------------------------|
| `ADMIN_EMAIL`     | `.env.local` | Email аккаунта владельца = админ |
| `SUPABASE_SERVICE_ROLE_KEY` | сервер только | Admin API Supabase          |

Документ для разработчиков: пример `.env.example` обновить без коммита секретов.

## Этапы разработки (станут задачами Task Master)

1. Добавить `ADMIN_EMAIL` и проверку `isAdminUser` на сервере.
2. Создать сервер-only клиент Supabase с service role (отдельный модуль,
   запрет импорта из `'use client'` компонентов — по возможности ESLint /
   соглашение в коде).
3. Страница `/admin` (или аналог): защита по сессии + по роли админа.
4. Загрузка и отображение списка пользователей через Admin API с пагинацией
   или лимитом.
5. Server Actions: блокировка / разблокировка с запретом действий над собой.
6. Server Actions: удаление пользователя с confirm на клиенте + каскад
   транзакций.
7. Ссылка в шапке только для админа; smoke-проверка: обычный пользователь
   не получает данные списка (не только UI).

## Чего НЕ делаем в этой версии

- **Несколько админов** и управление ролями через БД/UI
- **История действий админа** (полноценный audit trail)
- **Вход «от имени пользователя»** (impersonation)
- **Гибкая RBAC** (роли `moderator`, `viewer` и т.д.)
- **Блокировка только приложения без бана в Auth** — в MVP достаточно бана
  на уровне Supabase Auth, если не возникнет отдельное требование

## Дополнительные правила

- Проверка роли админа **всегда** на сервере перед любым Admin API вызовом.
- Email администратора задаётся владельцем в `.env.local`; в репозиторий
  реальное значение **не** коммитить.
- После мутаций — `revalidatePath` для админ-страницы (и при необходимости
  кэшей, если появятся).
